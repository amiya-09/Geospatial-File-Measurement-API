# Geospatial File Measurement API: implementation plan

Source: `Geospatial File Measurement API.docx` (project files).

## 1. Requirements checklist

- [ ] FastAPI backend (Python)
- [ ] `POST /api/files/` accepts `.zip` (Shapefile) or `.kml`, processes it
- [ ] Per feature: id/index, geometry type, geometry (GeoJSON), CRS, properties
- [ ] Polygon → area, LineString → length, Point → no measurement
- [ ] Unsupported geometry types handled gracefully (no 500s)
- [ ] Never measure in degrees: reproject to a projected CRS first (strategy is ours to choose and justify)
- [ ] `GET /api/files/{id}/` → id, filename, feature_count, crs, status
- [ ] `GET /api/files/{id}/measurements/` → per-feature measurements
- [ ] README: setup, API with examples, architecture (structure, file flow, measurement flow, CRS handling), design decisions and alternatives, learnings, future scope
- [ ] Public GitHub repo

Our own additions (cheap, high signal): tests, clear error responses, upload size limits, `GET /api/files/` list, OpenAPI docs (free with FastAPI).

## 2. Architecture

One FastAPI app, layered, synchronous processing inside the upload request.

```
HTTP (routers) → FileService → parser (KML | Shapefile ZIP) → normalised Features (shapely + WGS84)
                             → measurement (per-feature local projection) → repository (SQLite)
```

- **Parsers** return one container, `ParsedFile(crs, features, warnings)`, never a bare tuple. `features` is a list of `Feature(index, source_id, geometry: shapely, properties: dict)`; `warnings` is a `list[str]`. Everything downstream is format-agnostic.
- **CRS pipeline**: source CRS → EPSG:4326 (lon/lat, `always_xy=True`) → per-feature local projected CRS for measuring.
- **Projection strategy** (the key decision):
  - Area: Lambert Azimuthal Equal-Area centred on the feature's centroid (equal-area by construction, works at any latitude incl. poles).
  - Length: Azimuthal Equidistant centred on the feature's centroid (UTM zone of centroid is the documented alternative).
  - Cross-checked in tests against `pyproj.Geod` ellipsoidal (geodesic) results; target < 0.1 % difference for features up to a few hundred km.
  - We always go through WGS84 even if the file is already projected, because a projected source such as Web Mercator (EPSG:3857) gives badly wrong areas.
- **Units**: metres and square metres in the response (`length_m`, `area_m2`), plus `unit` fields and the measurement CRS used, so nothing is implicit.
- **Persistence**: SQLite via SQLAlchemy. Two tables: `files` (id UUID, filename, format, crs, status, feature_count, error, warnings JSON, created_at) and `features` (file_id, index, geometry_type, geometry GeoJSON, properties JSON, measurement JSON). Status: `PROCESSING → COMPLETED | FAILED` (see Failure policy below).
- Sync processing is deliberate: small files, simpler to test. Background processing goes in "future scope".

## 3. Dependencies

Runtime: `fastapi`, `uvicorn[standard]`, `python-multipart`, `sqlalchemy`, `shapely>=2`, `pyproj`, `pyshp`, `defusedxml`.
Dev: `pytest`, `httpx`, `ruff`.

No GDAL/geopandas/fiona: pure pip wheels, installs anywhere, and we control KML parsing. Trade-off (noted in README): fewer formats for free.

## 6. Highest-risk issues

**CRS / units**
- Axis order: EPSG:4326 is officially lat/lon; always build transformers with `always_xy=True` or every result is silently wrong.
- Shapefile with no `.prj`: default to EPSG:4326 only if all coordinates fall within lon/lat bounds, and record a warning; otherwise the file is unmeasurable: persist a `FAILED` record and return 422 (see Failure policy).
- `.prj` WKT (ESRI flavour) must be parsed with `pyproj.CRS.from_wkt`/`from_user_input`; report an EPSG code when `to_epsg()` resolves, else the CRS name.
- Projected sources in feet (US survey feet): handled by reprojecting via WGS84 rather than trusting native units.
- Features crossing the antimeridian or very large features (continent-scale): local projection error grows; document the limit, test that geodesic and projected agree within tolerance for realistic sizes.

**Shapefile ZIP validation**
- Zip-slip paths, zip bombs (cap compressed and uncompressed size, entry count), encrypted or corrupt zips → 4xx with nothing persisted (see Failure policy), never 500.
- Required trio `.shp/.shx/.dbf` (case-insensitive), optional `.prj/.cpg`; files inside a subfolder; `__MACOSX/` junk.
- Multiple shapefiles in one zip: default to rejecting with a clear message (alternative: process all layers).
- Read in memory or a temp dir, never extract to user-controlled paths. DBF encoding from `.cpg`, fallback UTF-8 then latin-1.

**KML parsing**
- Namespaces (KML 2.2 / 2.1 / `gx:`), nested `Document`/`Folder`, `MultiGeometry`, `Polygon` with `innerBoundaryIs` holes.
- `coordinates` is `lon,lat[,alt]` separated by arbitrary whitespace; altitude dropped.
- Properties from `name`, `description`, `ExtendedData/Data` and `SchemaData/SimpleData`.
- XXE / billion-laughs: parse with `defusedxml`.
- KMZ is out of scope for the minimum; cheap to add later (it is a zip with `doc.kml`).

**Geometry handling**
- Invalid polygons (self-intersections, unclosed rings): measure `make_valid` output and report `is_valid=false` plus `validity_reason` per feature, rather than crash. `make_valid` may return a `GeometryCollection` (polygons plus stray lines/points): measure the polygonal parts only and ignore the rest.
- Z/M coordinates: drop with `shapely.force_2d` before any projection or measurement, so altitude never leaks into transforms or lengths.
- Multi-geometries and GeometryCollections: sum parts per measurement type; Points/MultiPoints get `measurement: null` with reason "not applicable"; unknown types get `null` with reason "unsupported".
- Empty/null geometries (shapefile null shapes) recorded, not dropped, so feature indices stay stable.
- Shapefile ring orientation for multipart polygons with holes: rely on pyshp's `__geo_interface__`, and test it.

## Defaults I picked (change any before we start)

- Local LAEA/AEQD per feature (not UTM) as the projection strategy.
- SQLite persistence, synchronous processing.
- Missing `.prj`: assume EPSG:4326 when coordinates fit, with a warning.
- Multiple shapefiles in one zip: reject.

## Failure policy

Two distinct failure classes, decided at the parse/measure boundary:

1. **Unreadable file** (corrupt or unsafe zip, wrong file type, unparseable XML, missing required shapefile parts, multiple shapefiles in one zip): respond 4xx with an error body and **persist nothing**. No file id is issued.
2. **Readable but unmeasurable file** (e.g. no `.prj` and coordinates outside lon/lat range, CRS that cannot be resolved): **persist a `FAILED` file record** with the error message and respond **422 including the file id**, so `GET /api/files/{id}/` can show why.

Successful files persist as `COMPLETED`, with any non-fatal issues in `warnings`.

## Response additions

- `GET /api/files/{id}/` gains a file-level `warnings: list[str]` (empty list when none), alongside id, filename, feature_count, crs, status (and `error` when `FAILED`).
- Each feature in `GET /api/files/{id}/measurements/` gains `is_valid: bool` and `validity_reason: str | null` (null when valid).

## Routing

Routes use the exact spec paths, trailing slash included: `/api/files/`, `/api/files/{id}/`, `/api/files/{id}/measurements/`. A test must call each path with `follow_redirects=False` and assert the response is not a 307 (FastAPI's slash redirect would otherwise mask a mismatch).

## Phase 2 working rules

- Test-first: write the failing test, see it fail, then write the code.
- Small commits, one per logical step.
- No features beyond this plan.md. Anything new gets proposed, not built.
- When finished, list every non-obvious decision made so it can go into `docs/decisions.md`.
